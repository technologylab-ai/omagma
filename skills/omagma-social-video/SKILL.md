# Omagma social videos

Produce a legible marketing film and concise accompanying feature bullets. Follow repository AGENTS.md and video/README.md. Keep application development, installation and release qualification outside this workflow unless separately requested.

## Establish the baseline and scope

- Find the last user-approved social film, not merely the latest export or application release. Consult private film history, dated feature journal and current-since-release notes when available, then confirm against actual artifacts and approval messages. Do not assume a version is still current.
- Collect improvements since that film. Choose features with clear visible benefits for demonstrations; put smaller changes in a short recap and accompanying post. Verify product claims against source/release notes. Avoid technical implementation commentary in the film.
- Read the relevant user feedback and inspect the approved films. Preserve praised design when revising pacing or clarity. Revise the smallest affected portion; reuse unchanged captures and approved audio rather than starting over.

## Direction and attention

The established project policy uses **actual Claude Opus 5.5 at xhigh** for visual design, animation, film direction and authored film copy, with independent **Astra xhigh** review and follow-up after material fixes. Retain evidence of the actual model used; a differently named subagent is not a substitute. If the requested model is unavailable, explain the limitation before proposing a different design authority. Engineering orchestration and capture fidelity repairs may be implemented separately.

Give Opus the user's exact feedback, relevant approved references, available genuine assets and resource constraints. It should own the source changes, not just offer advice that another model replaces with its own design. Inspect its rendered compositions before the full export.

The approved visual language uses the magma atmosphere, strong type, glowing seams, contextual zooms and a warm orange guide. Keep it when the user approves it. The important attention pattern is:

1. Build a feature headline and its supporting line over the animated atmosphere, with the previous UI gone.
2. After the text settles, allow about **1.5–2 seconds** to read it.
3. Reveal the actual application, hold a readable before-state, then show the action and its result.
4. Hold the explanatory text fixed throughout that demonstration. Brief action keycaps can precede actual presses.
5. Close the UI before the next explanatory text builds. A payoff is not an excuse to animate new commentary over ongoing UI action.

These are attention principles, not a mandatory shot count, duration or separate chapter-slide deck. Let the interface action carry the demonstration once the feature is announced. Budget result-reading time as well as entrance motion.

Use large, contextual native crops instead of shrinking whole screens. The approved 1080p film targets roughly29–31px native text; treat26px as its review floor, not a universal font rule. Preserve pane borders and enough context to explain where the action happens. Keep camera rectangles separate from tighter spotlight rectangles. Switch native captured states atomically so glyphs never blend between two screens.

The guide must point beside content without sweeping through glyph centers: that looks like strike-through. The approved ember travels in the margin outside the native frame; a recorded pointer can guide a real mouse action. Do not compete with that pointer using a second guide.

## Tell an immediately understandable story

- Name an everyday case prominently when generic wording is ambiguous. “Booked a haircut?” distinguishes adding an already-booked personal appointment from responding to a meeting invitation. Do not market “no email/reply sent” as a generic Calendar benefit.
- Show a feature clearly before demonstrating an edge case. A red now line between events is easier to recognize than starting with it underneath meeting text. An overlap comparison is optional.
- Finish the largest action with meaningful populated output. A delivered Sent message with its actual shared file/link is stronger than a huge empty Inbox crop. Avoid following nearly empty UI with a redundant nearly empty catchphrase card; transition deliberately into useful recap or the close.
- Do not imply unlimited attachment sizes, public Drive sharing, completed AI notes, meeting monitoring or guarantees beyond the implemented product. Scope image paste and Meet settings accurately without turning the film into documentation.

## Genuine captures and bounded production

Use the relevant existing film tooling rather than recreating the application with HTML. Read [production.md](references/production.md) when capturing, rendering or encoding.

Capture the verified application executable with fictional providers, isolated PTYs and an isolated browser. Preserve exact frame/tape/image bindings, genuine interactions and independent outcome receipts. Never use personal mail, the user's clipboard or production account mutations for promotional captures. Do not fabricate native UI pixels, delivery results or clock readings. Capture adapters may faithfully reproduce terminal cells, colors and font metrics.

Inspect host activity and acquire the repository's cooperative host lock before heavy work. Keep ownership through cleanup. Respect the user's host constraints: the established conservative Linux setup uses one browser/page/render worker, two logical CPUs, low priority and a sampled4GiB aggregate-RSS watchdog. Recheck any remote host before use; availability is not permission to consume all its resources.

Preserve the approved soundtrack unless the user requests a music change. Reuse an appropriate already-approved duration when the new story needs more time. Do not silently splice, stretch, speed up or re-encode approved AAC; verify copied packet contents and timestamps. Keep earlier cuts and failed evidence.

## Review and deliver

Complete cheap syntax, replay, binding and relevant layout/attention checks before full rendering. For a revision, repeat checks affected by changed inputs; do not recapture or requalify unchanged application features merely because the film changed.

Review actual composed images, not only metadata or QA labels. In particular, a blank native row can have correct underline attributes while its browser replay shows no line. Inspect the visible pixels. Check actual opacity, clipping and transforms when testing settled text and UI visibility.

Use a short encoded transition preview when motion is uncertain. Freeze source, assets and audio before the full export. Inspect the final encoded movie at normal1x speed, including announcement/action boundaries and the last result→recap transition. Automated playback evidence does not establish that anyone listened to the audio.

Deliver a uniquely named local movie, poster, concise social copy and useful review artifact. Verify copied files and preserve previous outputs. Use the user's established destination when known. Open the video when requested, or when that preference is already established for the active review. Distinguish local delivery, user approval and public posting. Creating a video does not authorize posting it.

Update the private feature journal and film history with baseline version, source/artifact hashes, review status and approval status. Keep private paths, raw receipts, captured account data and generated media out of public commits. Record new demonstrated lessons narrowly; do not accumulate hypothetical rules or restart the workflow for minor feedback.
